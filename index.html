Replacing a third-party product customizer

Project charter, work breakdown structure and roadmap for an in-house customizer on a print-on-demand leather bag store.

Nguyễn Thùy DungProject ManagerA self-directed practice project

Overview

The store sells custom leather bags in the US. Customers add a name and pick an artwork, and a print-on-demand (POD) supplier prints each order. The customizer is a third-party Shopify app. The project replaces it with a tool the company owns and controls, while the Shopify store keeps running.

The problem

Customers can’t see a preview while customizing, which causes about 10 complaints a month. Ops pull each design file by hand, so wrong files lead to reprints and re-shipping. Repeated reports to the vendor brought no lasting fix.

The goal

An in-house customizer with a real-time preview, plus a bulk tool that creates one file of design links matched to order numbers.

Team and deadline

1 tech lead, 2 developers and about 100 ops hours. The current app must be switched off before 1 Mar 2027, with an extension to 1 May possible.

Ways of working

Agile with 2-week sprints, weekly priorities, daily standups focused on blockers, and a sponsor checkpoint on 10 Dec.

In scope

  • Real-time preview while customizing, on desktop and mobile
  • Artwork library and upload tool for ops
  • Custom name saved with the order
  • Design file generated per order
  • Bulk create: one file of design links with order numbers

Out of scope

  • Other product page features: buy more get more, upsell, add-to-cart and buy-now buttons
  • Automatic sending of files to the POD supplier (backlog, because ops should keep checking orders first)
  • Migrating all 300 products at launch: the 30 best sellers (over 50% of revenue) go first, and ops move the rest in waves

Constraints

  • Current app off before 1 Mar 2027; the latest is before the 1 May fee cycle (27 Apr)
  • No go-live or customer-facing change from mid-Nov to early Jan (sale season)
  • The current app runs in parallel for at least 2 weeks after go-live
  • Run cost after go-live about $1,100 a month; payback estimated at 4–8 months

Assumptions and PM authority

  • Files must match the supplier’s format (verified with a demo file)
  • Ops can run the tool without dev support (verified in ops testing)
  • The vendor will help back up old order data (verified in writing by 22 Oct)
  • The PM can approve decisions that don’t change the total budget and stay inside the internal team

What the plan shows

The baseline leaves almost no slack: the build finishes in mid-January, testing runs into Tet, and the parallel run ends right at the deadline. That is why the 10 Dec checkpoint exists, to ask the sponsor for the extension to 1 May before it is too late.

If time runs short

Ship the preview first, since it fixes the customer experience, and keep making fulfilment files manually for a while. Defer lower-priority scope before adding people or pushing past the freeze.
